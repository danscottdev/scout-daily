Deep dive: Steal the Claude Code team's review stack

2026-10-17

Anthropic's monorepo went from about 2,500 changes landing per day in May to more than 30,000 in September. Nobody reads that line by line. The Claude Code team's answer, laid out in a 14-minute engineering post by Addy Osmani, Morgan Westlee Lunt, and Qing Wang, isn't "skip review." They moved most of the reading to machines, aimed human attention at risk, and made rollback cheap. Their reported result: merged PRs more than doubled from June to September while the share that had to be reverted fell by more than 40%.

The reframe: optimize for human attention, guarded by reverts

Their goal is that most PRs merge with at most one human in the loop, and that human can be the author, with no rise in reverts or incidents. They measure human approvals per PR (median and 95th percentile), human comments, and how long PRs wait on a person. Revert and incident rates are the guardrail: if those go up, you didn't save time, you just moved it to cleanup. That's the part most teams skip. Write down that metric pair before you change anything.

The layers

1. Verify before a PR exists. Give the agent something it can run (tests, a build, a screenshot to compare against the design) and make it show the output instead of claiming it's done. Then have a subagent review the diff with fresh context. Many engineers also run internal skills before opening a PR: one hunts bugs, one simplifies the diff, one checks behavior end to end. Boris Cherny estimates verification alone makes results two to three times better.

2. Fix repeat findings at the source. When the reviewer keeps flagging the same thing, fix it in a skill, a lint rule, or the instruction files. CLAUDE.md stays short and points to other docs. REVIEW.md, written by code owners, says what failure looks like in that area ("it lies" for docs, "it misroutes" for config), caps nits, lists paths to skip, asks for file-and-line evidence, and asks for a summary that opens with a count and says plainly when nothing needs fixing.

3. AI review on every PR, with voting. Several agents hunt bugs in parallel, then a separate group votes on each finding, and it only posts if enough agree. Style-only and cleanup findings get dropped; they A/B tested those filters on their own PRs. Findings are tagged Important, Nit, or Pre-existing, so an old bug doesn't look like the author's fault. Every finding must be answered, either fixed or resolved with a reason. In the preview, the share of internal PRs getting substantive comments went from 16% to 54%.

4. Security review that blocks. A PR can't merge while any bug or security finding is still open. Closing a thread with a short reason is how you clear a false positive, and a later commit that fixes the issue clears it automatically. The open-source security review GitHub Action and /security-review give you the same setup outside Anthropic.

5. Normal CI, plus a rollback question. Lint, types, tests on every platform, and a build. The PR template asks how the change was tested and how to undo it. Claude can draft the answer, but the person who asked for the change signs off.

6. Human approval scaled by risk. Docs, copy, internal-only features, and additive changes behind a flag need no human approval once automated review and security checks pass. Riskier areas, like an auto-updater, get more human scrutiny. Repo owners decide which low-risk changes can merge on automated checks alone, and they say that line keeps moving.

How I'd roll this out for a client

  1. Baseline first. Pull 60-90 days of PR wait time, approvals per PR, and revert rate from the GitHub API. Without that, you can't prove the change worked.
  2. Verification habits in week one. Add a "show me the test output" rule plus a fresh-context subagent review to the team's agent config. This is cheap and needs no new vendor.
  3. Write REVIEW.md per area with the code owners. Keep each one short and specific about what failure looks like. This is where your consulting judgment earns its fee.
  4. Turn on automated PR review (Claude Code Review, or GitHub's AI Scan for infra-heavy repos) in Standard mode. Use Deep only where one missed bug costs more than the wait. Make findings blocking-until-answered, not blocking-forever.
  5. Write a risk table mapping paths to the human approvals they need. Start conservative and loosen it only while the revert rate holds.
  6. Review the metrics monthly. If reverts rise, tighten the risk table before you blame the tool.

Caveats: Code Review needs a Team or Enterprise plan, GitHub hosting, and isn't available with Zero Data Retention, the HIPAA configuration, or customer-managed encryption keys (docs). Regulated clients may need the local /code-review command or the open-source security Action instead. The numbers are Anthropic's own and from a team that builds the tool, so treat them as an upper bound and measure yours.
