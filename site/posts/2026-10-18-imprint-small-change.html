Deep dive: Imprint's small-change gate (steal this for clients)

2026-10-18

Yesterday's Scout deep dive covered how the Claude Code team doubled merged PRs while cutting reverts: verification before the PR, multi-agent review with voting, blocking security review, and human approval scaled by risk (Anthropic's post). Today Will Larson published the other half of that design — what happens when the low-risk bucket actually auto-merges. Imprint's small-change is a CI-gated eligibility check plus an AI skill that may only approve or ignore. No comments. No meat-proxy theater. Early on, about 10% of changes qualify.

The problem: more merges, better quality, slower reviews

Imprint's average engineer merges 4x more PRs than two years ago. Two teams are at 10x. One engineer is at 25x the weekly merges of the average engineer from two years back. Quality moved with volume: incidents down 42% half-over-half, critical incidents down 78%. The bottleneck is review wait. p50 review time went from about 33 minutes to about 77 minutes, and the slope tracks merge volume tightly enough that Larson made it a priority for the week.

They still believe in the four classic reasons for review — knowledge sharing, preventing errors, catching malice, and compliance — but argue each has a better modern mechanism (clustered review, CICD plus harness verification, path rules plus abuse detection, and controls that can be rewritten). The point of small-change is not "skip review forever." It is to validate a narrow, contained practice while those replacements get stronger.

Eligibility is a CI check, not a label you can slap on

When a PR is marked ready, CICD decides whether it is a small-change. That shows up as a passing GitHub check. There is also a label for visibility, but humans cannot make something eligible by editing the label — the check is independently verified by the build. All of these must hold:

  • Under 1,000 lines of code
  • No p1 or p2 findings from their ai-code-review bot
  • Author has "experience": 10+ prior merges into each affected service or application's directories
  • Impacts fewer than N distinct services (N=1 on the frontend monorepo; N=3 on the backend, where a typical change touches a gRPC service and a shared HTTP gateway)
  • Shared libraries and utilities are ineligible
  • Per-repo .small_change path exclusions for sensitive areas (money movement is the example)

Slack automation tags PR references with reacji for state (failing tests, approved-but-waiting, ready to merge) and now a small-change reacji so the channel can see which PRs are in the fast lane.

The skill: approve or ignore — never comment

Two internal skills ship across harnesses:

review-small-change takes a list of repos and walks open, non-draft small-changes. It may approve if checks pass (including the small-change check) and the diff does not touch sensitive topics like payments or security. Critically, it has only two outcomes: approve or ignore. It never leaves comments.

review-pr-cluster reviews batches of PRs for common themes and suggests discussion or new verifications — knowledge sharing at cluster scale, which is Larson's answer to "we used to learn one PR at a time."

The no-comments rule is the design's sharp edge. Larson calls the failure mode meat proxy review: the team is drowning in reviews, so people run a local harness that dumps comments; authors cannot tell which comments the human actually stands behind; teams then use harnesses to reply to harness comments; the whole thing looks like review and teaches nothing. In every case he has seen, the better move is to invest in centralized review, teach the harness to address that feedback, and stamp approval. review-small-change is built to refuse that trap.

Own the failures at the system level

Social contract: any error caused by a small-change is a failure of the system — ai-code-review, verification, CICD, or the harness — not a reason to yell at the author or abandon the gate. That is how you expand the 10% without pretending humans will catch what the machine missed on the other 90%. Implementation took about two days of intermittent attention; Larson expects to tune the knobs for a long time, maybe forever.

They also run a centrally orchestrated harness, fleet (in the spirit of Stripe's Minions), that can write and verify changes in a controlled cloud environment and pick how many independent reviewers a change needs — sometimes as low as one human reviewing what fleet wrote. That is the high-control path; small-change is the high-volume, low-ceremony path.

How this pairs with yesterday's Anthropic layers

Map the two posts onto one client stack:

  1. Verify before the PR (Anthropic) — tests, builds, fresh-context subagent review
  2. Automated PR review with severity (Anthropic Code Review / client's bot) — findings that must be answered
  3. Blocking security review (Anthropic) — open security threads block merge
  4. Risk table + eligibility gate (Imprint small-change) — CI decides which PRs may skip a human; skill may only approve or ignore
  5. Human attention on the rest — cluster review, path-based required reviewers, compliance repos that still need an independent human

Anthropic's post says repo owners decide which low-risk changes can merge on automated checks alone, and that the line keeps moving. Imprint is a concrete, published version of that line: LOC cap, experience threshold, service fan-out, shared-lib ban, path exclusions, and a skill that cannot invent a review theater.

Client rollout checklist for the agency

  1. Baseline. Pull 60–90 days of p50/p95 review wait, merges per engineer, revert rate, and incident rate. Without that, you cannot prove the gate helped.
  2. Write the risk table with code owners. Paths that move money, auth, crypto, PII, infra, and shared libraries stay out of small-change. Everything else starts conservative.
  3. Automate eligibility as a required check. Labels are for humans; the check is the source of truth. Do not let authors self-declare.
  4. Ship ai-code-review (or Claude Code Review / equivalent) first. p1/p2 findings must block small-change eligibility. If the bot is weak, the gate is unsafe.
  5. Build the approve-or-ignore skill. Ban comments in the skill itself. If the team wants feedback, route it through the centralized reviewer, not a local harness dump.
  6. Experience gate. Start at 10+ merges in each touched service. Lower it only after false-reject volume is measured.
  7. Declare the social contract in writing. Small-change incidents are system bugs. Track them as such and feed them into verification and the bot.
  8. Expand from ~10% only while reverts and incidents hold. Widen N, raise the LOC cap, or shrink exclusions one knob at a time. Review metrics monthly.
  9. Compliance carve-out. Repos whose controls still require an independent human stay out until legal rewrites the control. Do not paper over SOX/PCI language with a skill.

Caveats: Larson's numbers are early ("too early to give a useful result") and from one company. Treat 10% as a starting share, not a target. Meat-proxy review will reappear the moment someone "improves" the skill by letting it comment — design that out. And uncomfortable culture pushback is expected; Larson notes that reevaluating long-held review dogma is both the energizing and the painful part of the cycle.
