Anthropic's engineering post from this week is one of the clearest signals yet that coding agents change the bottleneck. In May they averaged about 2,500 merges a day to the monorepo. By September it was over 30,000. Claude was writing the code; source control, CI, and review tooling were choking. They spent five months building Scion, an in-house VCS, plus Antique (code review), search, and IAM, and fully migrated off git. Updated Oct 15 with more prior-art notes on Meta's Mononoke/Sapling techniques.

What broke

Main-branch history alone was nearly 100 GB; a compressed working copy over 25 GB. CI alone did on the order of 25 million checkouts a day. Naive fetch math: hundreds of petabytes of git traffic. They tried the standard monorepo toolkit — shallow clones, sparse checkouts, promisor remotes, internal mirrors (hundreds of them), seed snapshots in blob storage — and it stopped scaling as merge rate climbed. Seeds went stale; history-dependent ops got brittle.

The punchline they land on: they were already running git as a centralized system with always-online agents and jobs, while paying for a design meant for offline, complete clones. So they flipped the assumptions.

Scion's design bets (steal the ideas, not the binary)

  • Clients are always online. Fetch what you need; don't pretend every agent needs a full repo offline.
  • Server does the heavy work. Commits, merges, rebases, blame, history live on the server. The client caches objects, lays out a working copy, and talks ergonomically to the API.
  • Source control as a query API. CI jobs that only need a diff or merge-base can ask the server — no checkout required.
  • Horizontal everything. No fully materialized copy anywhere; content-addressed data; caches answering immutable object fetches. They report ~200× less CPU/memory than the git-mirror fleet, and checkouts in seconds instead of minutes (CI got a ~25% CPU capacity win).
  • Sparse and virtualized by default. Pay for files you touch. Skip working copies when an API answer is enough.

Anthropic is blunt: Scion is not a git replacement for normal teams. It only makes sense for enormous monorepos with huge agent traffic, and it pulls code review, search, and CI along with it. They're not shipping it as a product. They want forges to steal the server-side RPC and cache ideas inside git.

The human job changed

Seven engineers built Scion and Antique in five months while merge volume rose 10×. Their own framing: Claude is better at writing the code than they are; humans supply system design, constraints, and the word "no." Agents will violate core invariants to satisfy a pattern that should never have been allowed. Review shifts toward intent and architecture, not line-by-line reading. They also run "superfan" Claudes — Slack-channel agents obsessed with one component's health charts — as a complement to traditional alerts.

Merge queues as we know them fray when thousands of changes land while tests run. Anthropic invested in post-merge and pre-deploy automated testing and let Claude fix conflicts faster than humans diagnose them. That is a culture change, not a feature flag.

Why it matters to you

You probably don't need Scion. You do need a checklist for the next client whose agent fleet starts melting CI:

  • Measure merges/day, checkout time, and mirror/seed lag before rewriting anything.
  • Prefer server-side diffs, sparse checkouts, and artifact caches over "every job clones main."
  • Separate "code volume" problems (VCS, CI capacity) from "review quality" problems (intent review, path-based permissions, semantic approval rules).
  • Sell an Agent-Scale DevEx audit: where will 5–10× agent output hit first — git, CI minutes, review SLA, or artifact storage — and what cheap git-compatible mitigations buy 6–12 months.
